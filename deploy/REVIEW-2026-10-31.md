# 性能、代码审查与访问链路检查

检查日期：2026-10-31。代码改动、生产构建和测试均在本地完成。home 仅做读取、计时与日志检查；没有重启服务、替换线上代码、修改 Tunnel 或 DNS。服务器真实笔记只用于目录扫描计时，没有复制或输出正文。

## 性能结论

| 项目 | 修改前 | 修改后 | 口径 |
| --- | --- | --- | --- |
| 首次进入首页/文件夹所需 JS | 约 900 KB | 约 292 KB | 构建产物未压缩体积，减少约 68%；文档组件按需下载 |
| 首屏 CSS | 约 65.7 KB | 约 34.1 KB | 公式和代码高亮样式随阅读器加载 |
| home 上 53 篇笔记的目录扫描 | 首次 166 ms；后续 79–82 ms | 缓存建立后 9–10 ms | 同机对比，各 5 次；不包括公网请求和 React 渲染 |
| 启动聊天数据 | 所有聊天正文、图片、思考和工具结果 | 标题、ID、模式、时间 | 打开某个对话时再加载其正文 |
| 进入知识库后的文件夹请求 | 额外一次 `/api/folders` | 目录与笔记合并为 `/api/library` | 文件夹页面不再额外等待一次公网往返 |

目录缓存只保留元数据，仍检查文件修改时间、变更时间与大小；外部编辑、移动、删除可以在刷新后被发现。没有缓存私人正文到共享目录接口。

静态资源和 JSON 已启用压缩；聊天 SSE 明确排除，避免压缩缓冲影响逐字显示。带内容哈希的 `/assets` 使用一年 immutable 缓存；HTML 必须重新验证。

## 已修复的问题

1. `src/components.tsx`、`src/MarkdownRenderer.tsx`、`vite.config.ts`：原本首页提前加载 Markdown、数学与高亮模块；改为动态加载，固定 React/JSX 运行时归属，避免打包器把基础运行时混入延迟加载模块。Markdown 组件增加 memo，输入、弹窗等状态变化时复用未变化的历史正文。
2. `server/storage.mjs`、`server/index.mjs`：原目录接口每次串行重读所有 Markdown。改为元数据缓存，新增统一目录接口，前端所有笔记/文件夹刷新使用同一结果。
3. `server/database.mjs`、`src/App.tsx`：原启动接口查询并传输所有聊天与图片。新增 `?summary=1`，前端按需读取正文；加入加载状态与请求序号，防止快速切换后旧请求覆盖当前页面。原完整聊天 API 保留兼容。
4. `server/storage.mjs`、`server/index.mjs`：原 `createOnly` 先检查存在再写入，同时新建可能互相覆盖。现在写完临时文件后原子创建硬链接，同名竞争返回 409，失败方不会覆盖成功方。临时文件与目标位于同一目录；部署文件系统需支持硬链接，home 的常规 Linux 文件系统适用。
5. `server/index.mjs`：Agent 返回 `null` 等工具参数时，后续读取 `args.path` 会再次异常并中断流。现在校验对象类型并作为工具失败返回，后续回复可继续。
6. `src/api.ts`：隧道或代理返回 HTML 错误页时，原界面出现 JSON 解析错误。现在显示 HTTP 状态和可理解的重试提示。
7. `package.json`、`package-lock.json`：依赖审计发现数学插件嵌套的旧 KaTeX 命中 GHSA-238p-pmpm-9mq7（低风险、依赖已有原型污染的前提）。将所有 KaTeX 对齐到项目直接依赖，消除旧副本，公式测试通过。没有采用审计建议中的插件大版本降级。

## 审查后仍需关注

- **公网部署的模型地址边界**：登录用户可以配置任意 HTTP(S) Base URL，服务端会携带用户配置的密钥向该地址及其重定向目标发送请求。配合开放注册，这提供了从服务器访问内网 HTTP 服务的入口。若允许不受信任的人注册，建议限制模型地址来源、阻止跳转绕过，或者关闭公开注册、改为邀请制。这一轮没有擅自改变支持本地模型的行为或注册规则。
- **共享笔记并发编辑**：已有文档明确采用最后一次保存覆盖；这次修复的只是“新建同名文件”的竞争。两个人修改已有同一篇笔记仍可能覆盖，建议下一步加入版本号/If-Match 与冲突提示。重命名的目标存在检查也不具有完整的跨进程事务保证；需要多人高并发使用时进一步处理。
- **长对话的流式写入成本**：服务端每秒保存进度会读取完整对话并重写全部消息，带多张图片时开销较大。后续应改为只更新正在生成的一条消息；SQLite 保留为本项目存储并无明显必要更换。
- **文件数量继续增长**：当前客户端目录与搜索仍加载全部笔记元数据，未做分页或虚拟列表。53 篇笔记的主要成本来自重复 I/O 与公网往返；达到数千篇后再考虑服务器搜索、目录分页和虚拟列表。

这些是基于当前代码与实测的审查结果，不等于完整渗透测试或所有缺陷已经排除。

## 公网访问慢的证据

- home 自身 `/api/health` 约 3–4 ms，服务正常；检查时负载约 0.15，约 997 MB 内存可用，没有看到 CPU/内存不足证据。
- 当前电脑访问公网域名的首次健康检查约 2.26 s（其中 DNS 约 0.37 s、TLS 建立完成约 1.34 s）；另外一组同进程请求约 1.50、0.68、0.97 s。这些仅代表当前电脑、网络和时段，不是所有用户的延迟分布。
- cloudflared 最近登记的四条连接均为 `lax01/lax07`，协议 `http2`。本次公网响应还出现过 `AMS` 边缘标记。它们表明当前链路涉及远端节点，但不足以精确还原完整路由或断言唯一慢因。
- 日志持续出现 `cfd-features.argotunnel.com` 通过 `127.0.0.53` 查询失败；当前系统上游 DNS 是 `192.168.40.1`，现场查询该名称也没有拿到记录。它是需要检查的 DNS/域名响应问题，但不能据此断言它直接造成每次网页请求延迟。不要直接更改整机 DNS 后承诺能解决网页慢。

代码优化可以减少资源、服务器工作量和请求次数；不能消除 Cloudflare 接入路径本身的跨区域延迟。

## 建议的访问方案

### 当前电脑能 `ssh home`：先用 SSH 转发验证

在当前电脑终端运行并保持窗口开启：

```sh
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:13001:127.0.0.1:3001 home
```

浏览器打开 `http://127.0.0.1:13001`，需要在该地址重新登录。这条链路绕过 Cloudflare，保持应用仅监听服务器回环地址，并且只在当前电脑回环地址开放转发端口。用这个页面和公网域名打开相同文件夹，可以直接比较 Cloudflare 路径的影响。如果 home 的 SSH 入口自身也依赖相同的慢路径，则这个比较的收益有限。

### 主要是自己或少量熟人使用

优先考虑 Tailscale/WireGuard，让设备尽量直连；需配置访问范围，应用仍通过受控反代或转发入口访问。Tailscale 能否直连取决于网络和 NAT，落到 DERP 中继后不保证提速。先验证实际连接类型与延迟再替代现有入口。

### 需要任何浏览器直接访问

根据实际访问者网络试用入口服务器。可以迁移整个应用到线路更合适的 VPS，或者使用 VPS 的 HTTPS 反向代理，通过 FRP/WireGuard 回源 home。前者移除家庭上行与穿透链路；后者仍受家庭网络和回源质量约束。先测常用网络到入口的 RTT、首字节、丢包与晚高峰，再决定是否付费；不按地区名称直接保证效果。

### 继续用 Cloudflare

1. 先上线并验收这次已测试的代码优化。
2. 检查 DNS 问题与 cloudflared 运行日志。
3. 受控比较 `auto`、`quic`、`http2`。官方文档说明 auto 优先 QUIC，UDP 不可用时回退 HTTP/2；当前使用 HTTP/2 并不自动说明配置错误。切换协议不能保证选到更近节点。
4. 现有 Tunnel 还承载 wenyan，修改连接器或重启会影响它，应安排维护窗口与回退路径。
5. 确认哈希静态资源缓存命中；账号、笔记、聊天 API 保持 no-store，不要使用全站 Cache Everything。

核对过的官方资料（通过直接下载文档读取；本次网页搜索工具返回 403）：
